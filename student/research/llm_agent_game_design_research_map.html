LLM / Agent × Game Design：相关研究地图

这份整理聚焦一个具体问题：如果我们想做“AI 与人一起设计并实现游戏的 Agent”，现有工作分别已经解决了什么？ 它们的核心机制是什么？又有哪些问题仍然没有被真正解决？

一句话结论： 研究已经从“LLM 能不能生成游戏”推进到“Agent 能不能反复实现—试玩—修复游戏”； 2026 年开始明显出现更强的 human-AI co-design 工作。但 设计意图如何长期保留、AI 什么时候该自己做/什么时候该问人、以及如何评价“玩家实际体验是否符合设计者意图”， 仍然是相对空缺的交叉区域。
规则 / Mechanics 自动开发 Playtest 闭环 Human-AI 协作 Design Intent 值得继续做的 Gap

先看整体演进

01 · GENERATE
把自然语言变成游戏 从生成 level，扩展到规则、代码和完整游戏。核心问题是“能不能生成出来”。
02 · ORCHESTRATE
让多个 Agent 分工开发 规划、写代码、审查、执行分开做，重点解决 hallucination、冗余和工程可靠性。
03 · CLOSE THE LOOP
生成后真的去试玩 不只看代码能不能跑，而是让 solver / GUI Agent 玩游戏，用实际行为反馈继续修。
04 · CO-DESIGN
AI 不只是自动做，而是和人一起设计 开始关注 ideation、设计支柱、用户反馈、创作控制权，以及 AI 应该扮演什么角色。

详细拆解

A. 从“生成内容”到“生成完整游戏”

Game Generation via Large Language Models

Hu, Zhao & Liu · IEEE CoG 2024
2024
规则 + LevelLLM Generation

它解决的问题：不再只问“LLM 能不能生成 Mario/Zelda 的关卡”，而是尝试让 LLM 同时生成游戏规则和关卡。

机制怎么做

作者用 VGDL（Video Game Description Language）作为中间表示，让 LLM 根据不同数量和类型的上下文 prompt 生成规则描述与 level。可以把它理解为：把“一个小游戏”压缩成较结构化的文本程序，再让 LLM 一次性写出来。

侧重是什么

重点是扩大 PCG 的生成对象：从 content generation 走向 game generation。它证明“游戏规则本身”也可以成为 LLM 的生成对象，而不只是固定规则下的地图。

不足 / 边界
  • 作者明确指出 hallucination 和 self-correction 仍是问题，复杂、多样游戏仍需要 human intervention。
  • 本质上还比较接近 prompt → artifact，没有形成“实际运行 / 试玩 → 定向修改”的强闭环。
  • 它回答的是“能不能生成规则”，没有回答“这些规则是否真正形成了设计者想要的体验”。
对我们的启发

如果现在只把创新点写成“我们的 Agent 还能生成 mechanics / rules”，已经不够；规则生成至少从 2024 年开始就已经是明确 research topic。

Source: arXiv:2404.08706

GameGPT: Multi-agent Collaborative Framework for Game Development

Chen et al. · arXiv 2023, revised 2025
2023 / 2025
Multi-AgentFull Development Pipeline

它解决的问题：一个 LLM 从头做到尾容易 hallucinate、重复做无用任务，因此把 game development 拆成多个专业 Agent。

机制怎么做

流程被拆成 planning → task classification → code generation → execution → summarization。系统里有 manager、engineer、reviewer、tester 等不同角色；同时用小型 expert models、review agents、模板和 code decoupling 去降低错误和重复。

侧重是什么

它更像“AI 软件开发团队”，核心 contribution 是 orchestration：如何让多个 Agent 按角色协作，把一段游戏需求转成开发任务并执行。

不足 / 边界
  • 它主要优化工程可靠性、hallucination 和 redundancy，而不是研究 human-AI creative partnership。
  • Human 多数时候是需求提供者，而不是持续参与设计决策的人。
  • “Reviewer 说代码对不对”与“玩家玩起来是不是设计者要的感觉”仍是两件不同的事。
对我们的启发

“多 Agent 分工”本身也很难成为主要创新。Agent 数量不是关键，关键应该是 为什么要分这些角色，以及它们解决了什么此前未解决的设计问题。

Source: arXiv:2310.08067

Mortar: Evolving Mechanics for Automatic Game Design

2026 preprint
2026
MechanicsEvolutionary Search

它解决的问题：把自动游戏设计再往前推一步：不是只拼已有机制，而是让系统通过代码生成与搜索去产生、修改、进化 game mechanics。

机制怎么做

LLM 直接生成/修改 Python 游戏代码，再把 mechanic generation 放进 evolutionary / quality-diversity search。系统通过 gameplay trace 和 mechanic importance 等信号评价候选游戏。

侧重是什么

重点是 Automatic Game Design：扩大可搜索的 mechanic space，让“规则创新”本身也成为算法可以探索的对象。

不足 / 边界
  • 更偏 autonomy：系统自己探索什么 mechanics 值得保留，人类共同创作不是主问题。
  • 作者也指出视觉丰富度有限，例如 rendering 修改不包含动画。
  • 自动评价一个 mechanic“有差异/有作用”不等于它和某个设计者的创作意图一致。
对我们的启发

如果你的系统未来也能改 mechanics，创新不能只是“Agent 会改规则”，而可以是“Agent 为什么改、这次改动对应哪条 human intent、什么时候需要人批准”。

Source: arXiv:2601.00105
B. 从“生成完就结束”到“生成—试玩—再修改”

ScriptDoctor: Automatic Generation of PuzzleScript Games via LLMs and Tree Search

Earle et al. · 2025
2025
Automatic PlaytestClosed Loop

它解决的问题：LLM 不应该写完游戏就交卷；生成的游戏应该能自动被编译、试玩，再根据失败信息继续修。

机制怎么做

LLM 生成 PuzzleScript 游戏；编译器把 error / warning 返回给 LLM。如果编译成功，就用 BFS 搜索玩家去尝试解关卡，并把 solvability、solution length、search complexity 再反馈给 LLM。Prompt 里还加入 human-authored games 作为 few-shot grounding。

侧重是什么

真正重要的是 verifiable closed loop：代码合法性由 compiler 检，游戏是否能过由 automated player 检。它是“自动游戏设计 Agent”很典型的一条路线。

不足 / 边界
  • 作者自己指出：solvability 并不足以判断 mechanic 是否“坏掉”或是否符合原本 intent。
  • 有些复杂游戏恰恰因为 broken mechanic 才变得“难解”，指标会被骗。
  • 受 PuzzleScript 的 2D grid puzzle 表示限制；真实玩家体验、视觉和 feel 很难覆盖。
关键 gap

Verifier 选什么，决定 Agent 最后会优化成什么。“能编译 / 能通关”很好验证，但“紧张感、惊喜、叙事揭示时机”很难写成一个简单 solver metric。

Source: arXiv:2506.06524

Agentic PCG: Procedural Content Generation via Tool-using LLMs

Jiang, Earle, Khalifa & Togelius · 2026
2026
Environment FeedbackTool UseLevel Design

它解决的问题：与其让 LLM 一次性吐出一个 level，不如让它像 Agent 一样持续观察环境、选工具编辑、看指标变化，再继续优化。

机制怎么做

游戏被包装成类似 RL environment。Agent 循环执行 Perceive → Reason → Plan → Edit；可以调用低层工具（放 tile、画线、patch），也能调用 BSP / digger 这类经典 PCG 算法。Environment 提供 tile count、connectivity、solvability，动态游戏还可提供 simulated gameplay feedback。

侧重是什么

最强的点是 agentic optimization + tools + explicit feedback。它把 PCG 从“生成器”变成了“会反复调工具的 level designer / optimizer”。

不足 / 边界（相对我们的方向）
  • 主要研究的是已有游戏规则下的 level/content，而不是从零决定“应该是什么游戏”。
  • 自然语言目标主要作为 objective；没有重点研究用户在中间什么时候介入、AI 什么时候应该 defer。
  • 容易计算的 functional constraints 很强，但较难表达“我希望玩家产生什么情绪/理解”。
最重要的借鉴

它的 loop 非常值得借：设计 Agent 不能只有生成，必须有可观察环境 + 可执行工具 + feedback。我们真正要换掉的是 feedback 的含义和 human 的位置。

Source: Project page · SSRN preprint

GUI Agents for Continual Game Generation / Play2Code

Huang et al. · 2026
2026
GUI PlaytesterCoding AgentMemory

它解决的问题：游戏代码“看上去没错”不代表真的能玩，所以让 GUI Agent 像人一样打开浏览器、点击、按键、观察结果，然后把体验中的 bug 反馈给 coding Agent。

机制怎么做

Game Agent 写/修 HTML 游戏，GUI Agent 只看界面并实际操作游戏。每轮 GUI Agent 产出 gameplay summary + actionable fix list，Game Agent 决定哪些反馈要修。系统还有 Episode / Skill / World 三层 memory，把当前任务经验和跨任务经验积累起来。

侧重是什么

这是目前非常关键的一步：把“play”变成 code generation 的反馈信号。PlaytestArena 还用 200 个 browser game tasks + gameplay rubrics 来评估游戏是否按预期工作。

不足 / 边界
  • 作者的 human comparison 显示：human-driven refinement 在所有轮次仍优于 GUI Agent，后期细微交互问题尤其容易被 AI 漏掉。
  • Rubric 大量聚焦 mechanics、controls、progression、visual feedback——非常适合“功能是否实现”，但仍不等价于复杂的 creative intent。
  • Human designer 不是 loop 里的核心 actor；它更像“AI 自己做 + AI 自己试玩”。
和我们最接近的地方

如果做游戏设计 Agent，automated playtester 基本已经是应有组件，而不是足够独立的创新点。更值得往前走的是：playtester 反馈如何对齐 human intent，而不是只对齐 prompt/rubric。

C. Human-AI Co-Design：人到底怎么参与设计

LLMs as Evolutionary Engines for Online Interactive Collaborative Game Design

Lanzi & Loiacono · 2023
2023
Interactive CollaborationConcept Design

它解决的问题：不是让 LLM 一次决定一个 game concept，而是让人不断对候选方案反馈，再让 LLM 做“重组和变异”。

机制怎么做

流程类似 interactive genetic algorithm：先有一批 candidate designs → 用户对设计做反馈 / 选择 → 算法选择更有希望的设计 → LLM 对它们 recombine / mutate → 再交给用户继续选。

侧重是什么

它很早就把 LLM 放进 human feedback loop，而不是纯自动生成。人负责“这个方向有没有意思”，LLM 负责快速扩大和变形 idea space。

不足 / 边界
  • 人的输入主要是对候选 design 的 preference，interaction 比较像“选哪个”。
  • 主要工作在 idea / concept 层，没有把设计决策持续传递到 implementation、playtest。
  • 没有细分哪些 decision AI 可以自主做、哪些应该主动问人。
对我们的启发

“Human in the loop”本身已经存在；更强的问题是 human 怎么 in the loop：只选方案、给 critique、批准改动，还是 Agent 根据 uncertainty 主动请求设计决策？

Source: arXiv:2303.02155

The Ink Splotch Effect: ChatGPT as a Co-Creative Game Designer

Anjum et al. · FDG 2024
2024
Co-Creative StudyDesigner Intent

它解决的问题：ChatGPT 真正放进一个 game designer 的工作过程中，到底擅长什么、不擅长什么？

机制怎么做

作者做了三类 prototype：baseline、human-designed、ChatGPT-guided。AI 会建议 feature、game feel、Unity C# 实现；人类研究者尽量按 AI 建议去实现，再让玩家盲评这些游戏。

侧重是什么

它不是在造一个复杂 Agent，而是在研究 LLM 作为“设计搭档 / muse”到底产生什么影响。尤其关注 designer intent、game feel、contextual judgment。

它暴露出的关键不足
  • LLM 能提出高层 idea，也能给部分代码，但容易缺乏具体项目上下文。
  • 在 game feel 上经常给出“加粒子 / 加音效”这种泛化建议，却不知道什么时候、怎么调才对。
  • 真实设计过程需要不断 playtest 后问“为什么这样感觉不对”，而 LLM 并没有直接感知游戏体验。
  • 研究者多次需要人工修 AI 给出的实现问题。
为什么它对我们的 idea 很重要

它几乎直接指出：设计 intent 不是一句 prompt；它散落在 mechanic、level、art、UI、feel 和一次次 playtest 的微调里。这正是 intent-aware agent 可以深入的地方。

Source: arXiv:2403.02454

SPINE: Mixed-Initiative Game Design Pillar Workflows

Geheeb et al. · FDG 2026
2026
Mixed InitiativeDesign Pillars

它解决的问题：把“游戏的核心设计方向”从散乱聊天变成显式的 Game Design Pillars，然后让 LLM 帮设计者检查、补充和判断新 feature 是否偏离这些 pillars。

机制怎么做

SPINE 对 pillar 做结构检查、改写、pillar set completeness / contradiction 分析，并用 pillars 去验证新 feature 是否和核心方向一致。研究还把工具带到 game jam，并访谈专业开发者。

侧重是什么

这是非常接近 Design Intent Representation 的工作：它不只让 LLM brainstorm，而是把“我们为什么做这个游戏”固化成可被后续 design decisions 查询的结构化文档。

不足 / 边界
  • 当前主要发生在 early-stage design / documentation，而不是实现和自动 playtest。
  • 论文明确提到 output quality、consistency、transparency 的不稳定。
  • 评估规模较小、偏 qualitative；目前更像 prototype / design space exploration。
  • 它会检查“feature 是否符合 pillar”，但没有持续追踪每一次 code / level / narrative 修改是否违反 intent。
对我们意味着什么

“显式存 design intent”本身不能说完全没人做。更强的创新可以是：让 intent representation 真正进入 agent execution loop，作为每次 action、playtest 和 human escalation 的约束。

Source: arXiv:2605.09767

AutoBG: A Board Game Design Assistant

Li et al. · 2026
2026
End-to-End Co-DesignCritic LoopPersona Feedback

它解决的问题：桌游设计不是一次 brainstorm，而是 idea → structured draft → rulebook → critique → revision → audience feedback 的长流程；AutoBG 尝试把整个流程连起来。

机制怎么做

四个核心模块：BG-Ideator 用多轮对话形成 structured design draft；BG-Realizer 写完整 rulebook；BG-Critic 找设计缺陷，并 gate revision，只有确认改进才保留；BG-Persona 用 150 个真实玩家 profile 模拟个体化反馈。

侧重是什么

它是目前最接近“完整 human-AI game design workflow”的一类工作之一，而且做了 30 人 user study。重点不仅是自动生成，也是降低 blank-page anxiety、帮助发现隐藏设计问题。

作者明确写出的限制
  • Physical Playtesting Gap：现在仍通过文本分析 rulebook，而不是实际把游戏玩起来；ergonomics、实时节奏、emergent strategy 很难从规则文本推出来。
  • Multimodal Gap：目前只处理文本规则，board layout、iconography、视觉主题没有进入统一设计过程。
  • Persona Depth：玩家 persona 不能充分捕捉群体互动、频率和长期变化的偏好。
为什么它是必须正面比较的 baseline

如果我们说“做一个会和人一起从 idea 走到完整游戏的 Agent”，AutoBG 已经占掉很大一块。因此差异最好落在：可执行 digital game、真实 playtest、动态 agency allocation、长期 intent preservation。

Source: arXiv:2606.01976

把这些工作叠在一起，真正还缺什么？

Gap 1 设计意图存在，但没有真正贯穿执行链路

SPINE 已经把 pillars 做成显式对象；但目前少有系统把 human intent 从 ideation 一直绑定到 mechanic → code → level → narrative → playtest 的每一次改动。

Gap 2 Human-in-the-loop 有了，但“什么时候该找人”还很粗

很多系统要么几乎全自动，要么每轮都让人选。真正 agentic 的问题可以是：根据 uncertainty、impact、reversibility 判断 ASK / SUGGEST / ACT / DEFER。

Gap 3 Playtesting 已经很强，但 verifier 仍偏“功能正确”

solvability、controls、win condition、visual feedback 都容易检查；“玩家什么时候理解反转”“紧张感有没有按预期建立”这种 experience trajectory 仍缺稳定表示与验证。

Gap 4 AI 会提出修改，但 creative ownership / control 仍难处理

一个 Agent 能自己修所有问题，不代表它应该自己修所有问题。创造性任务中，“不擅自替设计者做高影响决策”可能本身就是系统能力。

一个比较有区分度的研究定位

不是再做一个“能自动生成完整游戏的 Agent”，而是研究：

How can an AI agent actively build and playtest a game while preserving human design intent and knowing when to return creative decisions to the human?

MECHANISM 1 Executable Design Intent
把 pillars / intent 变成每次 Agent action 都要检查的约束，而不是只放在文档里。
MECHANISM 2 Adaptive Mixed Initiative
Agent 根据 decision 类型选择 Ask / Suggest / Act / Defer，而不是固定交互节奏。
MECHANISM 3 Experience-aware Playtest
Playtester 不只报告 bug，还比较“实际玩家认知/体验轨迹”和设计者原本希望发生的轨迹。
