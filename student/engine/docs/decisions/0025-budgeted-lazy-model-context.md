# ADR-0025：按节点懒加载对话并使用可观测的预算化模型上下文

- 状态：Accepted
- 日期：2026-10-23
- 决策者：产品负责人
- 关联：[ADR-0018](0018-research-data-logging.md)、[ADR-0020](0020-review-model-and-reproducibility-metadata.md)

## 背景

教练对话、答案提炼和单项审查此前先读取项目全部消息，再在 Worker 内按节点筛选最近 10–20 条；Workspace 首屏也返回项目全部聊天。项目增长后，数据库读取、响应体和浏览器状态都会随无关历史线性增长。模型上下文使用固定消息条数而非 token 预算，且正式答案按字符串题号排序，可能形成 `Q1, Q10, …, Q2` 的顺序。`model_calls` 只记录供应商报告的总 token，无法解释一次调用包含了多少答案或历史消息。

## 决定

1. 所有节点对话查询由数据库按 `project_id + question_id` 过滤，倒序限制条数后再恢复时间顺序；复用现有复合索引。
2. Workspace 只返回有对话的节点 ID，不再返回全部消息；浏览器在打开问题或审查项时通过 `/api/messages` 懒加载该节点最近的消息。
3. 新增统一的 Model Context Builder。历史对话同时受最大消息数和估算 token 预算约束，最新用户请求始终保留。
4. 普通教练与答案提炼只把已确认答案作为正式全局状态，并严格按 protocol 顺序排列。全局 Design State 审查仍读取全部已确认答案，不改成局部审查。
5. `model_calls` 记录 `context_strategy`、包含答案数、包含消息数、估算上下文 token 和是否截断；供应商返回的 `input_tokens` 仍是实际计费与实验分析的主要值。

## 原因

- 在数据库层过滤可以避免读取与当前节点无关的消息；
- 懒加载防止首屏响应随完整对话历史持续膨胀；
- token 预算比固定消息条数更能控制真实上下文大小；
- 只发送已确认答案维持“AI 建议不能自动成为正式状态”的产品边界；
- 上下文组成元数据使后续 full-context 与优化策略实验可以解释 token、延迟和质量差异。

## 后果

- 打开一个尚未加载的节点时会多一次轻量 API 请求；
- 当前懒加载接口最多返回最近 100 条消息，更早消息暂不在 UI 展示，但仍保存在数据库和研究导出中；
- token 预算使用本地保守估算，不能替代供应商 tokenizer；实际 token 继续使用模型响应中的 usage；
- Context Builder 目前只优化历史消息选择，尚未根据答案语义选择相关答案。

## 验证方式

- AI 路由不再查询项目全部消息后在内存筛选；
- Workspace 响应的 `chats` 为空，只包含 `chatQuestionIds`；
- 打开问题时 `/api/messages` 返回该节点消息并恢复时间顺序；
- 模型上下文中的答案按 Q1、Q2、… 顺序排列，draft 不进入正式全局状态；
- 新模型调用在研究导出中包含上下文策略与组成字段；
- typecheck、lint 和全部 Vitest 测试通过。

## 回退方式

可以让 Context Builder 使用更高预算或 full-context 策略，而不恢复全项目消息查询。若懒加载接口出现问题，可临时在 Workspace 中只内嵌当前活动节点消息，但不应恢复返回全部项目历史。
