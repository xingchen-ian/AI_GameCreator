# ADR-0005：分步生成并原子保存完整 GDD

- 状态：Accepted
- 日期：2026-10-12
- 决策者：产品负责人 / Codex
- 关联：生产环境完整 GDD 请求在 55 秒模型超时处被中止

## 背景

原实现把六个阶段摘要、13 个 GDD 章节和全局一致性审查放在一次模型请求中，并允许最多输出 7200 tokens。生产日志显示 `/api/gdd` 连续在约 55.08 秒返回 500，与后端 `AbortSignal.timeout(55_000)` 完全一致。单纯延长等待时间仍会让一次请求承担全部失败风险，页面也无法说明当前进度。

## 决定

把 GDD 生成改为四阶段浏览器编排协议：

1. 生成标题、一句话概念和六阶段摘要；
2. 并行生成两批 GDD 章节；
3. 使用答案与完整章节执行全局一致性审查；
4. 校验答案 revision 未变化后，一次性保存 Design Snapshot、Stage Summary、GDD 和 Issues。

每个模型步骤使用较小的输出预算和独立的 48 秒超时。网络错误或 502/503/504 会自动重试一次。页面显示当前阶段和百分比；前面步骤成功但后续失败时，不会写入半成品 GDD。

## 原因

- 让每个模型请求的输出范围明显小于原来的完整 bundle，降低达到超时的概率；
- 把章节批次并行执行，避免分步后总等待时间线性增加；
- 保存前再次核对答案 revision，防止生成过程中答案变化造成错误版本对应；
- 保留 Design State → Snapshot → GDD 的原有版本语义；
- 用户能看到进度，并能获得明确的超时反馈。

## 考虑过的替代方案

### 只把超时从 55 秒提高到 120 秒

没有采用。它会掩盖单次请求过大的根因，失败时仍需全部重做，也没有进度反馈。

### 在 D1 中持久化每个中间生成步骤

暂未采用。它能跨刷新恢复，但需要新增生成任务状态机、清理策略和数据库迁移。第一版先采用客户端短流程编排；若真实使用中仍频繁中断，再升级为可恢复任务。

### 后台异步任务完成后轮询

暂未采用。当前 Sites Worker 和产品交互更适合多个短 HTTP 请求；引入队列或 Durable Object 会明显增加运维复杂度。

## 后果

### 正面影响

- 不再由一个 55 秒长请求承载整份 GDD；
- 两个章节批次可并行完成；
- 只有所有步骤成功才创建新 GDD 版本；
- 错误能区分配置问题、步骤超时和普通生成失败。

### 代价与风险

- 完整答案会在多个模型步骤中重复作为输入，输入 token 数高于单请求方案；
- 页面刷新会丢失尚未保存的中间结果，需要重新开始；
- 并行章节可能存在语气差异，因此最后仍必须经过全局审查；
- 免费额度结束后，需要根据实际成本考虑缓存阶段摘要或持久化中间结果。

## 受影响位置

- `app/api/gdd/route.ts`
- `lib/server/model-provider.ts`
- `components/workflow/workflow-app.tsx`
- `components/workflow/gdd-panels.tsx`

## 验证方式

- 构建与类型检查通过；
- 页面生成时依次显示阶段摘要、章节、审查和保存进度；
- 每个模型调用的输出预算与超时独立；
- 修改答案后继续旧生成会得到 409，不会保存不匹配版本；
- 任一步失败时 `gdd_versions` 不新增记录；全部成功后只新增一个完整版本。

## 回退方式

恢复单一 `game_design_document_bundle` 请求和旧版前端调用即可；数据库结构没有因本决策发生变化，不需要数据迁移。
