# ADR-0039：动态 GDD 大纲与固定语义覆盖合同

## 状态

Accepted，2026-10-24。本文取代此前 GDD 必须使用 13 个固定章节的实现决定；Design State、全局冲突审查和 Build Brief 的既有职责不变。

## 背景

旧版 GDD 把 21 道设计题重新分配到 13 个固定章节。该结构便于确定性检查，但会让不同类型的游戏使用同一组织方式，也容易在“核心循环”“规则状态”“行动后果”等章节重复描述同一机制。为了填满固定章节，模型还可能把证据不足的内容扩写成看似已经确认的设计。

完全自由的文档同样不可取：系统将无法稳定检查关键内容是否遗漏，Build Brief 也失去可追踪的信息合同，研究数据之间难以比较。

## 决定

- GDD 不再规定章节名称、数量和顺序。模型根据当前游戏生成 5–10 个动态章节。
- 系统固定要求整份文档覆盖八类语义：游戏概念、目标玩家体验、玩家与情境、核心玩法、规则与限制、反馈与后果、进程与结果、原型验证。
- 覆盖标签是整份文档的信息合同，不是章节模板。一个章节可以覆盖多个标签，同一标签也可以分布在多个章节。
- 每个动态章节保存稳定英文 `key`、中文 `title`、`coverageTags` 和 `sourceQuestionIds`。章节正文由后续批次按已确认大纲生成。
- 第一阶段同时生成标题、一句话概念、六阶段研究摘要和动态大纲。六阶段摘要继续用于研究数据与阶段状态，但不再决定 GDD 结构。
- 章节生成只返回 `key`、正文和证据题号；服务端从已确认大纲附加标题与覆盖标签，防止正文调用擅自改变文档结构。
- 保存前检查章节 key 唯一、数量为 5–10，并确认八类语义全部覆盖。
- 忠实度审查根据当前文档的动态 key 构造 Schema，不再使用固定章节枚举。
- 大纲和章节批次均保留严格 Schema、本地校验和一次结构 repair。模型首次不合规时才增加调用。
- 已保存的旧版 GDD 可以继续读取、编辑和执行忠实度检查；不迁移历史数据。

## 原因

- 文档结构能够反映具体游戏真正重要的机制，而不是重复题目结构。
- 固定语义覆盖保留了遗漏检查、证据追踪、研究比较和 Build Brief 可靠性。
- 大纲与正文职责分离后，正文生成不能静默改名或增删章节。
- 兼容旧数据，避免为了展示结构变化而修改数据库。

## 考虑过的替代方案

### 保留 13 个固定章节

没有采用。它稳定但僵硬，并会鼓励重复和无证据扩写。

### 完全自由生成 Markdown

没有采用。无法对遗漏、证据来源和后续编辑建立可靠的机器检查。

### 每种游戏类型维护一套模板

没有采用。用户的设计可能跨类型，模板选择本身会提前替用户定义游戏。

- `app/api/gdd/route.ts`
- `components/workflow/workflow-app.tsx`
- `components/workflow/gdd-panels.tsx`
- `lib/design/gdd.ts`
- `lib/design/types.ts`
- `lib/server/model-provider.ts`
- `tests/smoke/protocol.test.ts`

## 验证

- 大纲只允许 5–10 个章节、唯一合法 key 和真实题号。
- 六阶段摘要必须分别覆盖 Stage 1–6。
- 动态章节整体覆盖八类必要语义。
- 每个章节批次逐一返回所请求的 key，不能添加、改名或遗漏章节。
- 忠实度 patch 只能指向当前 GDD 中真实存在的动态 key。
- 旧版没有 `coverageTags` 的已保存 GDD 仍可打开和检查。
- TypeScript、lint、测试与生产构建通过。

## 回退

恢复固定 `gddSectionPlan` 和旧版生成编排即可。新增的 `coverageTags` 存在于 `sectionsJson` 内，不涉及数据库列或迁移；旧代码会忽略该字段。
