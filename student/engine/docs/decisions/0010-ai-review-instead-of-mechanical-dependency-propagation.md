# ADR-0010：答案修改不再机械传播“待复核”状态

- 状态：Accepted
- 日期：2026-10-17
- 决策者：产品负责人 / Codex
- 关联：ADR-0006 中关于依赖图传播的部分决定
- 后续调整：全局审查中的多项修改现在可以集中处理，未命中同一目标答案的建议不会因第一条写入而全部失效，见 [ADR-0013](0013-batched-global-review-revisions.md)。

## 背景

旧实现使用一张静态问题依赖图。任何问题答案变化后，系统都会递归找到预设的全部下游问题，并把已确认答案改成 `needs_review`。这种做法不理解实际修改内容，会把“可能相关”机械地呈现成用户必须处理的任务，增加跳转和重复确认，也不能提供具体修改建议。

理想方案是每次修改后由 AI 读取完整 Design State，判断真正受影响的答案并给出建议。但这会在每次保存时增加一次长上下文模型调用，带来明显等待、费用和失败面，因此不放入当前版本的即时保存路径。

## 决定

- 删除静态 `dependencyGraph`、递归 `getAffectedQuestions` 和 `markAnswersForReview`；
- 用户在单题页或全局审查中写入一个问题答案时，只修改该答案，不改变其他问题状态；
- 删除 `needs_review` 作为当前应用状态和所有对应 UI；通过数据迁移把历史 `needs_review` 状态统一改为 `confirmed`，只改状态、不改答案、修订号或其他记录；读取层同时保留兼容归一化，避免未迁移环境被旧值卡住；
- 问题答案变化后，现有阶段总结、GDD 和 Build Brief 仍标记为 stale，因为它们来自旧答案快照；
- 未采用的旧全局审查建议标记为 stale，避免继续套用旧基线上的建议；
- 只有用户主动重新生成 GDD 时，AI 才基于全部最新答案重新执行全局一致性审查并产生新的冲突集合；
- 暂不在每次答案保存后自动调用 AI 做相关性审查。

## 原因

- 静态依赖图只能表示“可能相关”，无法判断一次具体修改是否真的影响下游；
- 待复核状态没有对应的具体原因和修改建议，会把系统不确定性转嫁给用户；
- 直接保存符合用户对表单编辑的预期；
- 把语义一致性检查集中在用户主动触发的 GDD 全局审查，可以控制等待时间与模型成本；
- 保留版本 stale 机制，仍能防止旧 GDD 或 Build 被误认为来自最新答案。

## 考虑过的替代方案

### 每次修改后立即调用 AI

暂不采用。它能更准确地找出相关答案并提出修改，但每次保存都需要长上下文推理，会显著增加延迟、费用和超时风险。未来可以改成一个显式的“检查这次修改影响”按钮，或短时间内合并多次编辑后再检查。

### 保留依赖图，只把提示变弱

没有采用。即使提示改成“可能受影响”，它仍会机械地产生噪音，而且不能解释具体影响。

### 只删除 UI，保留生成阻断

没有采用。隐藏状态但继续阻止生成会让用户更难理解为什么流程无法继续。

## 后果

- 修改答案后不会再出现橙色“待复核”节点；
- 用户可以直接重新生成 GDD，AI 在生成流程的全局审查步骤中重新检查全部冲突；
- 某个相关答案不会被系统提前提醒，直到用户主动执行全局审查；
- 模型调用次数不因普通保存操作增加；
- 历史 `needs_review` 数据在部署时一次性清理，答案和修订历史保持不变。

## 验证方式

- 修改任意问题后，其他问题仍保持已确认且不会出现待复核提示；
- 迁移前后答案文本和修订号一致，历史 `needs_review` 状态变为 `confirmed`；
- 修改后旧 GDD 显示过期，并可直接点击“重新生成并审查”；
- 重新生成时 AI 使用全部最新答案产生新 GDD 与新冲突集合；
- 旧的未应用全局建议不能继续覆盖新基线；
- 构建、Lint 与线上 Worker 检查通过。

## 回退方式

恢复静态依赖模块、`needs_review` 状态、两个写入路由中的传播调用，以及对应 UI 和生成阻断。迁移只把旧状态改为 `confirmed`，没有删除任何答案；若回退后确实需要恢复待复核标记，必须重新计算，不能从已迁移数据中推断原标记。
