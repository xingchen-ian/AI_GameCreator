# ADR-0006：把全局 GDD 审查提升为独立节点，并通过确认式 Patch 同步设计

- 状态：Accepted
- 日期：2026-10-13
- 决策者：产品负责人 / Codex
- 关联：用户反馈“跳回去后不知道哪里要改，也没有修改建议”
- 后续变更：关于静态依赖图与下游待复核传播的部分已被 [ADR-0010](0010-ai-review-instead-of-mechanical-dependency-propagation.md) 替代；其余全局审查与确认式 Patch 决定继续有效。
- 后续变更：关于冲突生成与题号证据的规则由 [ADR-0011](0011-ai-grounded-conflicts-without-categories.md) 进一步规定。

## 背景

原界面把全局冲突放在右侧 GDD 小面板中。冲突卡只提供证据、影响和“返回 Q×”按钮，用户仍需自己定位答案中的具体问题、推导修改方案，再手动改写节点。这对新手不构成完整的设计支持闭环，也让全局审查在信息架构上显得像文档附属功能，而不是跨越六阶段的重要活动。

## 决定

在左侧六阶段流程之后增加独立的「GDD 全局审查」系统节点。它不是 Stage 7，不改变六阶段 protocol，而是读取所有阶段、完整 GDD 和冲突记录的跨阶段审查层。

该节点在中间主工作区提供专用 AI 对话。AI 可以生成结构化修改建议，每条建议包含：

- 目标类型：问题答案或 GDD 章节；
- 目标节点 ID；
- 修改前完整内容；
- 建议后的完整替换内容；
- 修改原因和关联冲突。

AI 不能静默写入。只有用户点击「确认并同步」后，后端才更新真实节点；用户也可以选择「暂不采用」。所有建议及其 proposed、applied、dismissed、stale 状态持久化保存。

## 原因

- 全局冲突需要在全局上下文中讨论，不应被拆回单题后丢失上下文；
- 给出可执行的修改前后对比，比只提供题号更适合新手；
- 用户确认后直接同步，减少“分析完还要重新找位置”的重复劳动；
- 确认式 Patch 保留用户作为设计决策者的控制权；
- 持久化建议能支持刷新、回顾和研究过程追踪。

## 考虑过的替代方案

### 继续增强右侧冲突卡

没有采用。右侧空间适合文档预览和状态，不适合长对话、多个修改方案及前后对比。

### 点击冲突后只自动定位到答案中的相关句子

没有采用。它能改善定位，但仍要求新手自己推导修改方案，不能解决核心问题。

### AI 自动覆盖所有相关节点

没有采用。跨节点修改会改变设计意图，也可能触发大量下游依赖；没有明确确认的自动覆盖风险过高。

### 把全局审查定义为 Stage 7

没有采用。原 protocol 的六阶段描述设计形成过程；全局审查是可以反复进入的系统层，不是线性的新阶段。

## 后果

### 正面影响

- 用户可以在一个上下文中理解冲突、讨论方案并应用修改；
- AI 建议能直接同步到问题答案或 GDD 章节；
- 应用前检查修改前内容，旧建议不会覆盖已经变化的新内容；
- 修改问题答案后仍遵守依赖图：受影响的下游节点进入待复核；
- 重新生成 GDD 或手动修改设计后，未应用的旧建议自动标记为 stale。

### 代价与风险

- 新增 `gdd_review_changes` 数据表和一个 AI 路由；
- 修改上游答案后，用户仍需确认受影响的下游节点，不能为了便利跳过依赖安全；
- AI 可能给出不合适的替换文本，因此 UI 必须始终展示 before/after；
- 当前 Patch 粒度是整段答案或整章替换，不支持句子级合并。

## 验证方式

- 左侧六阶段之后出现独立的全局审查节点；
- 节点中的 AI 对话可以返回 0–4 个结构化修改建议；
- 修改建议刷新后仍存在；
- 点击应用后，相应问题答案或 GDD 章节更新；
- 目标内容已经变化时返回 409 并把建议标记为 stale；
- 上游答案更新后，下游依赖节点进入待复核；
- 重新生成 GDD 后，上一版本未应用建议失效；
- 构建、Lint 和本地 D1 迁移验证通过。

## 回退方式

隐藏全局审查节点与新 API 即可恢复旧 UI。`gdd_review_changes` 是附加表，不影响既有答案、GDD 或 Build Brief；回退时可以保留该表以保存历史，之后再单独决定是否删除。
